# libmon hook list for a glibc x86-64 Linux guest.
# Passed as `--so-hooks-list` by `sandboxd.guests.argv_trace` whenever the
# `libmon` plugin is selected. The Windows counterpart is `hooks.txt`, passed
# as `--dll-hooks-list`; the grammars match, the contents do not.
#
# Format (src/plugins/libmon/README.md in the drakvuf submodule):
#   <so name>,<function name|hex offset>[,no-retval],<log|log+stack>[,<arg>,...]
#
# <so name> matches a prefix of the basename of the mapped path, so
# "libc.so.6" matches /lib/x86_64-linux-gnu/libc.so.6 and "libssl.so" also
# matches a versioned libssl.so.3. Matching is case-sensitive.
#
# Each <arg> is [Name:]type. Only some types change formatting -- lpcstr
# reads a NUL-terminated string, pulong/pulonglong dereference a pointer --
# and any other name documents the signature while the raw value is printed.
#
# ---------------------------------------------------------------------------
# WHAT IS DELIBERATELY ABSENT, AND WHY
#
# **Hot functions are not hooked.** One Dom0 core saturates per concurrent
# trace and measured syscall throughput is 415-856/s (CURRENT-STATE.md, and
# `12-baremetal-trial.md` Part H). A breakpoint on `strcmp`, `memcpy`, `read`,
# `write`, `getc` or `putc` fires thousands of times per second in ordinary
# library code and would cost far more than the trace is worth. capa's rule
# set names several of them; they are dropped here on purpose, and a future
# generator over capa-rules must keep dropping them.
#
# **Kernel symbols are not hookable here.** capa-rules names `commit_creds`,
# `prepare_kernel_cred` and `nf_register_hook` for rootkit detection. libmon
# resolves symbols in a shared object's own `.dynsym` at its load address --
# userspace only -- so those belong to `syscalls`/`ebpfmon`, not here.
#
# **MSVC CRT names are not libc.** `_wsystem`, `_wmkdir`, `_allmul` and
# friends appear in capa-rules because the same rule covers Windows; there is
# no such symbol in glibc.
#
# **Android is not a target of this file, and the paths here are the second
# reason.** BlissOS links bionic: there is no `libc.so.6`, and its linker does
# not export `_r_debug`, so libmon v1 cannot arm there at all (measured
# 2026-09-26 -- see the `_ANDROID_PLUGINS` comment in `sandboxd/guests.py`).
# A bionic hook list would key on `libc.so` and `libdl.so` under
# `/apex/com.android.runtime/lib64/`, and is worth writing only once libmon
# can attach.
# ---------------------------------------------------------------------------

# --- HTTP via libcurl ------------------------------------------------------
# **Hand-authored, and necessarily so.** capa-rules v9.4.0 contains no curl,
# OpenSSL or gnutls `api:` feature at all -- every HTTP API it names is
# winhttp/wininet/httpapi or .NET -- so nothing can be derived from it here.
#
# `get_http_info` replays these as a handle chain, the way it replays
# WinINet's on Windows: `curl_easy_init` returns a handle, `curl_easy_setopt`
# accumulates options onto it, and `curl_easy_perform` is the moment a request
# actually happens. The option NUMBERS are read there (get_http_info
# .CURL_OPTIONS) because libcurl's ABI fixes them.
#
# `Value:lpcstr` is right only for the string options (URL, user agent,
# referer, custom verb). For a long option the same bytes are printed as a
# string and will look like garbage; that is preferred to dropping the URL,
# and `get_http_info` keys on the option number rather than on the rendering.
libcurl.so.4,curl_easy_init,log
libcurl.so.4,curl_easy_setopt,log,Handle:lpvoid,Option:int,Value:lpcstr
libcurl.so.4,curl_easy_perform,log,Handle:lpvoid
libcurl.so.4,curl_easy_cleanup,log,Handle:lpvoid

# --- TLS payloads via OpenSSL ----------------------------------------------
# Plaintext at the library boundary, before encryption -- the only place an
# HTTPS request body is readable without the session key. `get_http_info`
# reads the first line of an SSL_write buffer and records it only when it
# parses as an HTTP request line, so an arbitrary TLS payload is not reported
# as a URL.
#
# A sample that uses OpenSSL directly rather than through libcurl is the case
# this covers; one that uses libcurl is already covered above, and will also
# appear here because libcurl calls OpenSSL underneath.
libssl.so,SSL_write,log,Ssl:lpvoid,Buf:lpcstr,Num:int
libssl.so,SSL_read,no-retval,log,Ssl:lpvoid,Buf:lpvoid,Num:int
libssl.so,SSL_connect,log,Ssl:lpvoid
